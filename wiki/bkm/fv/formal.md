# Formal verification

How to choose where formal verification pays, write properties and assumptions from the spec, read proofs, bounded proofs, covers and counterexamples honestly, and keep the properties in line with the RTL. Simulation is in [verification.md](../dv/verification.md); a counterexample whose cause is not obvious goes to [debugging.md](../debug/debugging.md).

## Rules

- Keep properties, assumptions and the formal setup under `src/<project>/fv/<block>/`, and the formal plan under `wiki/src/<project>/fv/<block>/`. For each property the plan records: the property and the harm in one plain sentence each, the spec line it comes from, the RTL files it covers, its assumptions, its result (proof, bounded proof to N cycles, cover), the command that runs it, and the sync commit at which it was last confirmed to describe the RTL. Why: a reviewer must trust and rerun the result without learning the property language, and the sync commit shows when the RTL moved past the property.
- Aim formal where a bug costs most and simulation reaches least: control logic, arbiters (mutual exclusion, fairness, no starvation), FIFOs and credit counters (no overflow or underflow, ordering, count matches occupancy), handshakes (valid held and payload stable until accepted, no lost or duplicated transfer), reset sequencing, the control side of clock-domain crossings (metastability itself needs the structural CDC checker), and deep corner cases that need a rare sequence of events. Choose the strongest such target in the block, not the easiest to prove. Leave wide datapaths and arithmetic to simulation or an equivalence checker. Why: formal checks every input sequence in its scope, which is worth most where random stimulus rarely reaches.
- Pick the tool kind by the question: a property checker on the RTL for "does this block ever break this rule", an equivalence checker for "do these two versions behave the same", a structural CDC or reset checker for crossings, and a model checker over an abstract state-machine model for a protocol or control scheme before or beside the RTL. Say in the plan which kind and why. Why: the wrong kind answers a different question at a higher cost.
- Write every property and assumption from the spec, citing the line, never from the RTL. White-box assertions on internal signals are allowed here ([test-behavior-not-implementation.md](../principles/test-behavior-not-implementation.md) factory-local note), but their expected behaviour still comes from the spec. Why: a property read off the RTL proves the RTL equals itself.
- Write an assumption only for what the spec says a neighbour block guarantees on an input, and check each assumption on the driving side: as an assertion in that block's formal setup, or as an assertion in simulation. Why: an assumption nobody checks is a promise nobody keeps.
- Never add or tighten an assumption, reduce a bound, or reword a property to make a counterexample go away, unless the spec forbids the input or the behaviour changed on purpose; cite the spec line or the issue. Why: over-constraining is the classic formal trap: it makes a proof pass by excluding the very inputs that break the design.
- Pair every property with covers that show the assumptions still allow the interesting cases: the FIFO reaches full, both requesters win, a transfer completes under back-pressure, reset lands mid-transfer. Treat an unreachable cover as a finding: an over-constrained assumption or dead logic. Why: a proof under assumptions that allow nothing is vacuous and still reports "proven".
- Report each result in its own words and never round up: **proven** means every depth; **bounded proof to N cycles** means no counterexample up to N, and you must state N against the design's own depth (FIFO depth plus pipeline latency, the longest timeout, the deepest counter); **covered** means reachable, not correct. Why: a bound shorter than the time to fill the FIFO says nothing about a full FIFO.
- You must show each new property failing on a scratch break of the RTL it guards (drop a check, reorder a step, change a counter bound), then drop the break. Why: a property never seen to fail proves nothing.
- Place fast bounded runs in L0 and full proofs higher, per [ci-levels.md](../workflow/ci-levels.md). Why: the level rules live in one place.
- Start every proof from the spec's reset state, and disable assertions and assumptions while reset is asserted. Why: a proof from an arbitrary initial state finds false counterexamples, and one that checks during reset tests behaviour the spec does not define.
- When a full proof does not converge, add helper invariants (provable properties that constrain the reachable state) rather than assumptions. Why: an invariant is itself proven; an assumption only narrows what is checked.

## Steps

1. **Choose the target.** From the spec and the issue, name the promise, the harm when it breaks, and why simulation is unlikely to reach the breaking case. Write it in the formal plan.
2. **Write properties, assumptions and covers** from the spec per the rules above. One property per rule; name each after the promise ("no_write_lost_when_full"), not the signal.
3. **Model a state machine when the behaviour is about order.** For a protocol or controller, list its states and the transitions the spec allows, write each rule as an invariant over those states, and let the model checker search. Make each model step one clock cycle of the RTL, or one atomic step the RTL takes, and point each state and transition to the RTL or spec that it stands for. The counterexample is the shortest path to a state that breaks a rule: tell it as numbered steps in the spec's words ("1. the producer writes while full; 2. the consumer pops in the same cycle; 3. the write is dropped"). When a captain must decide whether a behaviour is right, give a state diagram labelled in the spec's words alongside the path. Why: a shortest path in plain words is something a captain can judge without the tool.
4. **Run and read each result.** For a pass, check the covers were hit and run the scratch break. For a counterexample, replay it against the real RTL step by step, ideally as a simulation test ([debugging.md](../debug/debugging.md) step 1). If a step cannot happen in the RTL or is excluded by the spec, the property or assumption is wrong: fix it, cite the spec, and say what was wrong. If every step can happen, it is a bug: state the harm in one sentence and fix it per [debugging.md](../debug/debugging.md), or open an issue if it is outside scope. Until a replay shows the bug, assume an abstract model is wrong, not the design.
5. **Bring properties back in line after the RTL changes.** When the covered RTL changed after a property's sync commit:
   1. Run the property as it is and record the result. A pass here only says the old description still holds; the dangerous case is a pass on RTL the property no longer describes.
   2. Read every change to the covered RTL since the sync commit, including renamed or moved logic and new logic that writes the guarded state. Classify each: no effect on what the property describes; the property's description of the RTL is stale (a step split in two, a new path to the guarded state, a changed range); the promise changed on purpose, with evidence in the issue or spec; or the promise may be broken.
   3. Update assumptions and the model from the RTL and spec before rerunning, never from what makes the run pass. Change a property only for a promise that changed on purpose; record the old wording, the new wording and the evidence. Keep the bounds; if one must shrink, say so.
   4. Rerun. Show a pass can still fail with a scratch break. Judge a failure by replay as in step 4: a failure from a stale description is drift in the properties; a failure every step of which happens in the RTL is a real bug. Name the commit that introduced it, and report it on the issue; do not weaken the property to land the realignment.
   5. Move the sync commit only for a property you confirmed describes the RTL at that commit.
6. **Report the evidence.** In the pull request's Evidence section ([landing.md](../workflow/landing.md)), give for each property: the result in the words above with bounds and the tool kind, the covers hit, the scratch break it caught, any counterexample now closed told as steps, the assumptions, and what the formal scope leaves out. For a property you realigned, say whether each failure was drift or a bug. Vet any runtime or capacity claim about the proof with [explain-the-number.md](../principles/explain-the-number.md).

## Exit criteria

- Every property, assumption and cover cites the spec, and every assumption is checked on its driving side or the plan says why not.
- Each property was seen failing on a scratch break, and each result is reported as proven, bounded to a stated N, or covered.
- Every counterexample was replayed against the RTL and closed as a fixed bug, an issue, or a corrected property with the spec reason.
- The formal plan's covered files, bounds and sync commits match the RTL at the pull request's head.
