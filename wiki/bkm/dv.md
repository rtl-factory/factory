# Simulation-based verification

How to verify a block in simulation: plan from the spec, write the failing test first, check through the block's interface, measure coverage honestly, and report the result as evidence. Formal verification is in [fv.md](fv.md); a failure whose cause is not obvious goes to [debug.md](debug.md).

## Rules

- Keep the testbench under `src/<project>/dv/<block>/` and the DV plan at `wiki/src/<project>/dv/<block>/dv-plan.md` ([standard documents](layout.md#standard-documents)), and change them in the same pull request as the RTL they check. Why: a plan that lags the RTL describes a block that no longer exists ([flow step 5](flow.md#steps)).
- You must write the failing test or check before the RTL change, run it, and see it fail for the intended reason: a scoreboard mismatch or assertion on the missing or broken behaviour, not a compile error, an X or a timeout. When the ports do not exist yet, add them first as a stub that drives reset values, so the red is a behaviour failure. Why: a test you never saw fail proves nothing, and a failure for the wrong reason hides that ([Sequence work into verifiable units](principles.md#sequence-work-into-verifiable-units): commit the failing test before the fix).
- Work one feature at a time: one test, the least RTL that makes it pass, then the next. Never write all the tests first. Why: tests written ahead of the design check its imagined shape, not its behaviour.
- Drive and check the block only through its ports, against its spec ([Test Behavior, Not Implementation](principles.md#test-behavior-not-implementation)). Model only what sits outside the block (the neighbours on its interfaces); never force or peek internal signals from the scoreboard. Why: a test pinned to internals breaks on every refactor and misses what a neighbour block sees.
- Derive expected values independently of the RTL: from the spec, a worked example, or a reference model written from the spec, never by recomputing the RTL's own logic. Why: a model that copies the design agrees with its bugs.
- Run every constrained-random test with an explicit seed that the log prints, and pin each regression to a fixed seed list, while the higher levels also run fresh random seeds, printed. Add every seed that ever found a bug to that list. Why: a failure you cannot rerun cannot be debugged or proven fixed, and a seed failure is a real bug, not a flake (["Getting it landable"](pull-requests.md#getting-it-landable)).
- Never weaken a check, widen a tolerance, add a coverage exclusion or drop a seed to turn a run green, unless the spec says the case is legal; cite the spec line. Why: a weakened check lands the bug it was written to catch.
- Treat coverage as a measured number you must explain ([Explain the Number](principles.md#explain-the-number)): name the holes and the reason for each, never only the percentage. Why: 95% says nothing about whether the missing 5% is the feature the issue is about.
- Run tests, seeds and waveforms through Bazel per [build](flow.md#build). Why: Bazel runs what CI runs and reruns only what changed.
- Place each test per [CI levels](flow.md#ci-levels): a directed smoke test and a few seeds per feature in L0, seed sweeps and long tests at the higher levels. Why: the level rules live in one place.

## Steps

1. **Plan.** Write or update the DV plan, `wiki/src/<project>/dv/<block>/dv-plan.md`, from the block's MAS (the HAS for a system testbench) and the issue's acceptance criteria. Give each feature one row: a short feature ID, the spec section it comes from, how it is stimulated, what checks it (scoreboard, reference model, assertion), the coverage points that show it was exercised, its tests, and its regression level. List the interface entry points (each port or transaction type a neighbour can use) and the corner cases: reset in mid-transaction, back-pressure, full and empty, simultaneous events, illegal or boundary inputs. Every acceptance criterion maps to at least one row. Why: the plan is how a reviewer sees which promise each test keeps, and an unmapped criterion is untested.
2. **Pick the stimulus.** Use directed tests for the cases the spec names exactly (reset values, a specific ordering, a reported bug) and for the first red of each feature. Use constrained-random stimulus for the space around them; write each constraint from the spec's legal input range, and add a coverage point for every corner the constraints must reach. Why: directed tests prove the named cases; random stimulus finds the ones nobody named, but only within what the constraints allow.
3. **Check.** Compare every output transaction in a scoreboard against the reference model or the expected values, and assert the interface protocol rules (handshake stability, no output while in reset) on the ports. At the end of each test, check that the scoreboard compared more than zero transactions and that nothing was left pending. Why: a checker that compared nothing passes every test ([Explain the Number](principles.md#explain-the-number): rule out code that never ran).
4. **Red, then green.** Run the new test against the current RTL and keep the failing output. Make the smallest RTL change that passes it, update the spec if the behaviour it describes changed, and rerun the test and L0.
5. **Prove the test can fail.** For each new checker, break the behaviour it guards on a scratch copy of the RTL (drop a write, swap an ordering, change an off-by-one) and confirm a test catches it; then drop the scratch change. Why: a test that also passes on broken RTL proves nothing ([Test Behavior, Not Implementation](principles.md#test-behavior-not-implementation)).
6. **Measure coverage.** Collect functional coverage (the plan's coverage points) and code coverage on the passing regression. For each hole, decide: a missing test (add one), a constraint that cannot reach it (fix the constraint), unreachable by the spec (exclude it with the spec reason in the plan), or dead RTL (open an issue). Report the number with the holes and their reasons. Why: a hole explained is a decision; a hole unexplained is a gap.
7. **Keep the plan honest.** When the RTL or spec changes, read every row the change touches and classify each mismatch: the plan describes the block wrongly (fix the plan), the testbench cannot drive a working behaviour (fix the testbench), or the RTL no longer does what the spec promises (a bug: report it on the issue, or open one if it is outside scope, and keep the failing test). Look for new ports, modes or transactions that no row covers; add a row only with the spec section it comes from. Why: a plan rots the moment the RTL changes, and a stale plan reports coverage of a block that no longer exists.
8. **Report the evidence.** In the pull request's Evidence section ([writing and landing](pull-requests.md#writing-and-landing)), give: the regression level run, the tests and seeds run and passed, the failing output before the fix and the passing output after, the functional and code coverage with each hole and its reason, the scratch break each new checker caught, and what was not run. When you claim a simulation runtime or throughput change, vet it with [Explain the Number](principles.md#explain-the-number): run count, spread and what limits it.

## Exit criteria

- Every acceptance criterion of the issue maps to a plan row with a passing test, and the plan matches the RTL and spec at the pull request's head.
- Each new test was seen failing for the intended reason before the RTL change, and each new checker caught a scratch break.
- Every random test is reproducible from its printed seed, and every bug-finding seed is pinned.
- Coverage is reported as numbers with every hole explained, and no check was weakened without a cited spec reason.
